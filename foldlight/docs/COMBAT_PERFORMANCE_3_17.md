# 无尽增援与多首领性能 · 3.17

2026-10-17，本机 Windows / Godot 4.6.3 原生调试引擎，OpenGL Compatibility，NVIDIA GeForce RTX 5070 Ti Laptop GPU / 580.88。窗口 1280×720，逻辑画布 1920×1080，前台窗口、未限制 FPS。测量期间无其他 Godot 测试同时运行。完整数据见 [COMBAT_PERFORMANCE_3_17.json](COMBAT_PERFORMANCE_3_17.json)。

## 方法与范围

使用扩展后的三张生产地图和真实共享战斗组件。静止无敌玩家装备全部 Lv.5 自动武器，普通敌人设置高生命以保持人数；首领使用实际第三阶段 AI、预警、攻击、碰撞和纸雕模型，保持高最大生命与 27% 生命比例，避免夹具提前结束。每个渲染帧补齐至 260 枚真实弹丸，原生固定物理步、自动武器、飞行、命中及地形碰撞照常执行，没有改成一帧只算一个物理步。

初始化后冻结任务计时、自动增援和环境事件调度，保留真实敌人行为与当前支援出生配额。多首领下的总人口配额分别为 32 和 24，**包含首领自身**。支援请求仍实际发出，但满额时不能越过人口上限。此夹具验证战斗人口上限下的压力，不代表一整局、移动操作、持续轰炸或手机温度场景。

每组至少 12 秒且至少 240 个渲染帧，去掉前 31 帧预热，统计墙钟渲染帧间隔。最后一轮实际取样 610 / 478 / 731 / 885 帧。Godot 自带 process/physics 监视器可能残留场景切换的时长，JSON 保留原始值，但结论只使用墙钟帧间隔。

双首领采用倒悬书记、断页行刑者，测量中实际发出 8 次攻击、10 次预警、3 次支援请求。三首领采用礁冠炮城、潮汐织母、蚀日双铃，实际发出 32 次攻击、14 次预警、4 次支援请求。首领持续处于战斗流程，不是静止展示模型。

第一轮独立复核的四组中位数为 16.989 / 20.515 / 15.420 / 12.954 ms，P95 为 21.117 / 30.979 / 18.797 / 16.689 ms。该轮最低弹数误包含初始化前的零弹状态，因此最终表格使用修正采样后的一轮；初始化样本没有纳入最终最低弹数。

## 判断

48 普通敌人拥挤上限的中位数约合 47 FPS，P95 帧间隔约 31.5 ms。可以保留为当前人口硬顶，但不能宣称该配置锁定 60 FPS。多首领出现时同步减少普通敌人，测量中确实将总负载限制在较低范围；不宜在此基础上再叠加完整普通波次。

3.16 的 36 敌 / 260 弹控制夹具曾测得中位数 18.763 ms、P95 27.456 ms。本次 36 敌参考数值相近，但地图已扩展、取样时长不同，不能将两次结果作为严格的版本性能增益百分比。没有重新把 84 个不死敌人集中围攻当成正常玩法；旧极端结果仍保留在 3.16 报告中。

本报告不据此保证低端设备、实体安卓手机长时发热或浏览器负载下的性能。APK 与浏览器仍需各自验证。
